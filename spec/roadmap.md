# Roadmap

---

## What This Agent Does

A local-first personal data-analysis agent. The user uploads a CSV/Excel file, the agent immediately auto-profiles it (columns, types, row count, missing values), and the user then has a natural-language conversation with the agent about the data — asking questions, requesting cleaning/transforms, and getting back plain-language answers with key numbers, the code that produced them, and per-query cost/token visibility. The agent reasons by writing and running real code (pandas) against the locally-stored file rather than guessing from a sample; raw row-level data never leaves the machine — only schema, column statistics, generated code, and aggregated results are ever sent to the LLM.

## Who Uses It

A single local user (just one person, a few times a day) who has data files (CSVs/Excel exports, e.g. monthly reports) and wants fast, trustworthy answers and light cleaning without opening a notebook. They return to the same dataset across multiple days, so history must persist across restarts.

## Core Problem Being Solved

Replaces manually opening a CSV in Excel/pandas to answer ad-hoc questions ("what's the average X by Y", "which rows look off", "clean this column and export it"). The agent does the coding, shows its work, and remembers the conversation — while keeping the user's raw data on their own machine and keeping LLM spend visible.

## Success Criteria

- [ ] User can upload a CSV or Excel file and see an accurate auto-generated profile (columns, dtypes, row count, missing-value counts) within seconds, with no manual step.
- [ ] User can ask a natural-language question about the uploaded data and receive a plain-language answer containing the *correct* key numbers (verifiable against the source file), backed by real pandas execution — not an LLM guess.
- [ ] The exact code that was executed is visible (collapsible) next to every answer.
- [ ] Every query shows its estimated cost and token usage, and prior questions/answers persist and reload correctly after an app restart.
- [ ] No raw data row is ever present in a prompt sent to the LLM — verified by an automated test that inspects the outbound LLM payload.
- [ ] (Phase 2) A dataset spanning multiple files (e.g. 12 monthly CSVs) can be analyzed as one dataset, and answers to aggregate questions are computed from the full unioned data, not a truncated sample.

## What This Agent Does NOT Do (Out of Scope)

- No external integrations (no Slack/email/BI-tool connectors) — this is a standalone local tool.
- No multi-user accounts, auth, or sharing — single local user, no login.
- No cloud storage of uploaded files — everything lives on the local filesystem/DB.
- No arbitrary code execution sandboxing against a malicious/untrusted third party — this is a personal tool where the executed code is generated by the user's own LLM call, not submitted by an untrusted party. Guardrails exist to catch LLM mistakes (e.g. accidental destructive calls), not to contain an adversary.
- No support for file formats beyond CSV and Excel (`.csv`, `.xlsx`, `.xls`).
- No real-time/streaming data sources — batch file upload only.

## Key Constraints

- **Raw-row privacy boundary (hard rule):** the LLM only ever receives schema, column statistics, generated code, and aggregated/truncated results — never raw row-level data. Enforced in code at `src/sandbox/executor.py::summarize_for_llm()` (see `spec/architecture.md`).
- **Cost visibility:** every query shows estimated cost + tokens used; a running total is visible for the session.
- **Full audit trail:** every query, the code executed, and the result are stored with timestamps in the local database and queryable later.
- **Performance:** typical questions on a few-MB-to-~100MB file answer in well under 30 seconds.
- **Local-first:** SQLite + local filesystem; only outbound network calls are to the Gemini API.

## Phases of Development

> **Phase 1 is the smallest first-time-right user-testable win.** It must work perfectly the first time the user tests it — zero rough edges on the tested path. Its backend is minimal but REAL on the one core path. Its frontend is visually complete: real UI for the one working path PLUS clearly-labelled NON-FUNCTIONAL stubs for everything coming later.

### Phase 1 — Upload, Profile, Ask, Answer

- **Goal:** the user uploads a single CSV/Excel file, sees an accurate auto-profile immediately, asks one natural-language question, and gets back a real plain-language answer (computed by real pandas code run against the real file, via the real Gemini API) with the code shown (collapsible) and the per-query token/cost estimate. Chat history persists in SQLite so the conversation survives an app restart.
- **Independent slices (parallel build units):**
  - `db-schema` (backend) — SQLAlchemy models + Alembic migration for `datasets`, `dataset_files`, `dataset_profiles`, `conversations`, `chat_messages`, `query_runs`. Deps: none.
  - `sandbox-executor` (backend) — the code-execution sandbox and the `summarize_for_llm()` raw-row boundary enforcement; pure functions, no DB/API dependency. Deps: none.
  - `analysis-graph` (backend) — the LangGraph state/nodes/edges/runner implementing the single-pass ReAct loop (see `spec/agent.md`), Gemini prompt templates, cost/token accounting. Deps: `sandbox-executor` (calls its `run_code`/`summarize_for_llm` functions).
  - `ingestion-profiling` (backend) — file upload handling, local storage layout, profiling logic, `POST /datasets`, `GET /datasets/{id}`, `GET /datasets/{id}/profile`. Deps: `db-schema`.
  - `conversation-api` (backend) — `POST /conversations`, `POST /conversations/{id}/messages`, `GET /conversations/{id}/messages`; wires `analysis-graph` + `db-schema` into the runner and REST layer. Deps: `db-schema`, `analysis-graph`.
  - `frontend-chat-ui` (frontend) — upload area, profile card, chat thread, collapsible code view, token/cost badges, single-step progress indicator, and the labelled non-functional stubs (charts, export, multi-file, audit-trail nav). Builds against the documented contract in `spec/api.md`. Deps: none.
- **Key surfaces / files:**
  - `src/db/models.py`, `alembic/versions/0001_initial.py` — replaces the generic `RunRow` with the domain schema in `spec/data.md`.
  - `src/sandbox/executor.py` — new module.
  - `src/graph/state.py`, `src/graph/nodes.py`, `src/graph/edges.py`, `src/graph/agent.py`, `src/graph/runner.py` — replaces the `transform_text` capability slot with the analysis loop in `spec/agent.md`.
  - `src/prompts/generate_code.md`, `src/prompts/compose_answer.md` — replace `src/prompts/transform.md`.
  - `src/domain/dataset.py`, `src/domain/conversation.py`, `src/api/datasets.py`, `src/api/conversations.py` — replace `src/domain/run.py`, `src/api/runs.py`.
  - `src/tools/profiling.py`, `src/tools/storage.py` — new modules.
  - `src/config/settings.py` — add sandbox/cost/LangSmith settings (see `spec/architecture.md`).
  - `frontend/src/app/page.tsx` (+ new components under `frontend/src/app/components/`) — replaces the transform-text form.
  - `tests/unit/`, `tests/integration/`, `tests/e2e/`, `frontend/tests/e2e/` — new tests per slice.
- **Gate command:** `uv run alembic upgrade head && uv run pytest tests/unit tests/integration -q` (runs against the real Gemini API using `AGENT_GEMINI_API_KEY` from `.env`, and the real SQLite DB file, never an in-memory/mocked provider for the integration suite) — **plus** `cd frontend && pnpm build && cd .. && uv run python -m src` then `npx playwright test frontend/tests/e2e/ --reporter=line` against `http://localhost:8001/app/`.
- **How the user tests it (handoff seed):**
  1. `uv run alembic upgrade head` then `uv run alembic current` (confirm a revision hash prints).
  2. `cd frontend && pnpm build && cd ..` then `uv run python -m src`.
  3. Open `http://localhost:8001/app/`.
  4. Upload a CSV or Excel file. Expected: a profile card appears immediately showing columns, dtypes, row count, and missing-value counts that match the file.
  5. Type a question about the data (e.g. "what's the average of column X" or "how many rows have a missing value in column Y") and submit. Expected: within ~30s, a plain-language answer appears with the correct number, a "View code" toggle reveals the exact pandas code that ran, and a small badge shows the token count and estimated cost for that query.
  6. Reload the page. Expected: the question and answer are still there (loaded from SQLite).
  7. **Labelled stubs (visibly marked "coming soon", non-functional, must not look broken):** a chart placeholder area below the answer, a disabled "Export cleaned data" button, a disabled "+ Add another file" control, a disabled "View audit trail" link.

### Phase 2 — Iteration, Multi-File, Charts & Audit Dashboard

- **Goal:** wires every Phase-1 stub into a real feature: the agent now iterates (writes code, runs it, inspects the result, and retries up to a step limit) with a live step list in the UI; it proactively suggests 2-3 follow-up questions and flags anomalies/data-quality issues after each answer; multiple files (or a folder of related files, e.g. 12 monthly CSVs) can be treated as one joined dataset; answers can include interactive charts; cleaned/derived data and analysis reports can be exported; and the full cost/audit-trail dashboard is browsable.
- **Independent slices (parallel build units):**
  - `iterative-loop` (backend) — raises `max_steps`, activates the `decide_next` loop-back edge and the `check_clarity` clarification branch in `src/graph/*`; adds proactive follow-up-suggestion and anomaly-flagging generation to `compose_answer`. Deps: none (extends Phase-1 graph in place).
  - `multi-file-join` (backend) — folder-as-dataset ingestion (`POST /datasets/{id}/files`) and dataset joins (`POST /datasets/join`) in `src/tools/`, `src/api/datasets.py`, plus re-profiling across the unioned data. Deps: none (extends Phase-1 ingestion in place).
  - `export-and-derived` (backend) — `POST /datasets/{id}/export`, `src/tools/export.py`, `DerivedDataset` persistence. Deps: none.
  - `audit-cost-api` (backend) — `GET /query-runs`, `GET /cost-summary`, session/day rollups. Deps: none (schema already exists from Phase 1).
  - `frontend-step-list-and-charts` (frontend) — live multi-step progress list, interactive chart rendering, follow-up suggestion chips, anomaly banners. Deps: none.
  - `frontend-multifile-export-audit` (frontend) — multi-file upload UI, export button wiring, audit-trail/cost-dashboard screen. Deps: none.
- **Key surfaces / files:** `src/graph/nodes.py`, `src/graph/edges.py`, `src/graph/state.py`, `src/tools/joins.py`, `src/tools/export.py`, `src/api/datasets.py`, `src/api/query_runs.py` (new), `frontend/src/app/components/StepList.tsx`, `frontend/src/app/components/Chart.tsx`, `frontend/src/app/audit/page.tsx`.
- **Gate command:** `uv run pytest tests/unit tests/integration -q` (real Gemini API + SQLite; the integration fixture uses a >12-file, >5,000-row synthetic dataset so a sampled vs. full-data aggregate answer is observably different) **plus** `npx playwright test frontend/tests/e2e/ --reporter=line`.
- **How the user tests it (handoff seed):**
  1. Ask a question that requires multiple reasoning/code steps (e.g. "clean up column X, then tell me the average of the cleaned values") — expected: a live step list shows "Step 1: writing code… / Step 2: running code… / Step 3: refining…" and the final answer is correct.
  2. After any answer, expect 2-3 clickable follow-up-question suggestions and, if applicable, a flagged data-quality note.
  3. Upload a second file to the same dataset (or point at a folder) — expected: the profile updates to reflect the combined row count, and a question spanning both files answers using the full combined data.
  4. Ask for a trend/breakdown — expected: an interactive chart renders alongside the numbers.
  5. Click "Export cleaned data" — expected: a downloadable CSV of the cleaned/derived dataset.
  6. Open the audit-trail/cost dashboard — expected: every past query, its code, its result, and today's running cost total are listed and searchable.
